================================================================================
  멀티유저 자동매매 시스템 — 전체 동작 흐름 정리
  (DeepSeek 브랜치 / 2026-06-04 기준)
================================================================================

이 문서는 "여러 사용자가 각자 자기 거래소 API 키로 자동매매하는" 시스템이
어떤 구성요소로, 어떤 순서로 돌아가는지를 정리한 것이다.


────────────────────────────────────────────────────────────────────────────
0. 한 줄 요약
────────────────────────────────────────────────────────────────────────────
- 사용자는 앱에서 (1) 거래소 API 키를 등록하고 (2) "매매설정"(심볼·전략·투자금·
  손실한도)을 만든다.
- Spring(백엔드)은 키를 암호화 저장하고, 활성 매매설정을 DB에 둔다.
- 통합 워커(trader, Node.js)는 활성 설정을 폴링해서, 신호는 한 번만 계산해
  공유하고, "주문/청산"할 때만 설정별 키·투자금으로 갈라서 실행한다.
- 손실한도 초과/비상정지(kill switch)는 DB가 권위를 가지며, 워커가 그에 맞춰
  포지션을 정리한다.

핵심 사상: "신호는 공유, 돈이 움직이는 주문만 사용자별로 분리."


────────────────────────────────────────────────────────────────────────────
1. 구성요소 (3개 레이어)
────────────────────────────────────────────────────────────────────────────

[프론트엔드]  frontend/ (React)
  - ApiKeyManager.tsx        : 거래소 API 키 등록/활성화/삭제
  - TradeConfigManager.tsx   : 매매설정 CRUD (심볼·전략·투자금·레버리지·손실한도)
  - KillSwitchPanel.tsx      : (admin 전용) 전체 비상정지 토글
  - AssetsPage.tsx           : 위 컴포넌트들을 'api-keys' 탭에 배치
  - LivePage.tsx             : 거래탭. 레거시 Bot1~7 대신 통합 워커 상태를 표시
  - CoinListPage.tsx         : 마켓탭 상단 총자산. 워커 snapshot의 mainBalance 기준
  - WorkerStatusPanel.tsx    : API 탭의 워커 상태/설정/포지션 관리 패널

[백엔드]  backend/src/main/java/com/tj/app/ (Spring Boot)
  - member/BotApiKey*        : API 키 암호화 저장(AES-256-GCM) + 슬롯 매핑
  - member/InternalBotCredentialController : 워커에 복호화 키 공급(내부 토큰)
       · GET /api/internal/bot-credentials/{slot}            (운영자 고정)
       · GET /api/internal/bot-credentials/by-member?...     (임의 회원 ← 멀티유저)
  - trade/TradeConfig*       : 매매설정 테이블/CRUD (/api/user/trade-configs, JWT)
  - trade/InternalTradeController : 워커 전용 내부 API
       · GET  /api/internal/trade-configs/active        (활성 설정 전체)
       · POST /api/internal/trade-configs/{id}/pnl      (실현손익 + 손실한도 자동중지)
       · PUT  /api/internal/trade-configs/{id}/status   (상태 보고)
       · GET  /api/internal/trade-configs/kill-switch   (비상정지 상태)
  - trade/InternalWorkerController : 워커 상태 push 수신
       · POST /api/internal/worker/status
  - trade/AdminController     : (admin)
       · GET/POST /api/admin/kill-switch
       · GET      /api/admin/worker/status
  - trade/WorkerStatusHolder  : 워커 snapshot 메모리 캐시(alive 판정 포함)
  - common/config/SystemFlagService + DdlAutoRunner : system_flags 테이블(kill_switch)

[통합 워커]  trader/ (Node.js, --experimental-strip-types)
  - unified-worker.ts        : 진입점. N개 설정을 1프로세스에서 운용 ★핵심
  - lib/market-feed.ts       : 공유 시세 (심볼 합집합으로 CandleFeed 1개)
  - lib/engine-registry.ts   : signature별 SignalEngine 공유 + 웜업 + 신호 fan-out
  - lib/signal-engine.ts     : 4h OB 감지 → 1h 진입/청산 판정 (전략 두뇌)
  - lib/order-executor.ts    : 실제 Bitget 주문 (creds/investUsdt/leverage 인자)
  - lib/bitget.ts            : Bitget REST 래퍼 (계정 API에 creds? 인자)
  - lib/credentials.ts       : Spring 내부 API로 복호화 키 로드
  - lib/config-loader.ts     : 활성설정 조회 + 상태/손익 보고 + kill switch 조회
  - lib/config-state.ts      : 설정별 런타임 상태(보유 포지션) 인메모리 저장
  - lib/warmup.ts            : Binance REST로 과거 캔들 주입(OB 히스토리 복원)

  워커 snapshot에 포함되는 핵심 값:
    · mainBalance       : MAIN 계정 Bitget 선물 USDT 잔고
    · mainPositions     : MAIN 계정 수동/외부 선물 포지션 목록
    · mainPendingOrders : MAIN 계정 수동/외부 선물 미체결 주문 목록
    · configs           : 활성 매매설정 + 포지션 보유 여부/진입가/TP/SL/수량
    · pendingOrders     : 거래소 미체결 주문 목록
    · trackers          : SignalEngine 트래커 상태(scanning/waiting_entry/active 등)
    · engineCount/symbols/killed

  ※ 레거시 bot.ts(단일 심볼·운영자 전용)는 그대로 보존. 통합 워커와 별개 진입점.


────────────────────────────────────────────────────────────────────────────
2. 사용자 관점 흐름 (셋업)
────────────────────────────────────────────────────────────────────────────

  (1) 로그인 → 'api-keys' 탭
  (2) Bitget API 키 등록
      → Spring이 AES-256-GCM으로 암호화해서 bot_api_keys 테이블에 저장
      → ※ 출금 권한 없는 키만 쓰도록 안내(법적/보안). 거래·조회 권한만.
  (3) 매매설정 추가: 심볼(SOL 등) + 전략(OB/FVG/BB) + 투자금(USDT) +
      레버리지 + 최대손실%(필수) + 활성 토글
      → trade_configs 테이블에 저장. (member, exchange, symbol) UNIQUE.
      → max_loss_pct 필수, 같은 회원 invest_usdt 합 ≤ 잔고 (검증)
  (4) 활성 토글 ON → is_active=true → 워커가 다음 폴링에 픽업


────────────────────────────────────────────────────────────────────────────
3. 통합 워커 동작 흐름 (런타임) ★
────────────────────────────────────────────────────────────────────────────

  [기동]
    main() → INTERNAL_API_URL/TOKEN 확인 → syncConfigs() 1회 → 폴링 루프 시작
      · 설정 폴링   : 8초 (WORKER_POLL_MS)
      · 포지션 폴링 : 20초 (WORKER_POS_POLL_MS)

  ┌─────────────────────────────────────────────────────────────────────┐
  │ syncConfigs() — 8초마다 (재진입 가드 있음: 한 사이클이 길어도 중복 X)│
  └─────────────────────────────────────────────────────────────────────┘
    ① GET /active 로 활성 설정 목록 조회
    ② GET /kill-switch — ON이면 active=[] 로 간주(=전부 정리 대상)
    ③ [사라진 설정] (삭제·STOPPED_LOSS·kill)
         보유 포지션 있으면 → executeSL2Exit(creds)로 시장가 청산 → settle()
         → registry.unsubscribe → store에서 제거
    ④ [새 설정]
         a. loadBotCredentialsByMember(memberId, symbol) 로 복호화 키 로드
            (실패 시 status=ERROR, 건너뜀 — env fallback 없음: 남의 키 오용 방지)
         b. registry.subscribe(cfg)  ← signature = hash(symbol+전략+params)
              · 같은 signature 엔진 있으면 공유(구독자만 추가)
              · 없으면 새 엔진 생성 → warmUpEngine(과거 캔들) → 그 다음 이벤트 배선
                (웜업 중 과거 신호가 fan-out돼 주문되는 사고 방지 ★)
         c. reconcile(st) — 거래소 실포지션 조회해서 인메모리 상태 복구
              (재시작 중복진입 방지 + 웜업 트래커와 mid 매칭 시 SL2 복구)
         d. status=RUNNING 보고
    ⑤ marketFeed.setSymbols(전 구독 심볼 합집합) — 바뀐 경우만 CandleFeed 재구축
    ⑥ buildSnapshot() → POST /api/internal/worker/status
         - admin 화면/거래탭/마켓탭/자산탭이 이 snapshot을 같은 기준으로 조회

  ┌─────────────────────────────────────────────────────────────────────┐
  │ 실시간 시세 → 신호 → 주문 (이벤트 기반)                              │
  └─────────────────────────────────────────────────────────────────────┘
    MarketFeed가 캔들 broadcast
      → registry.feed(candle) → 해당 심볼 엔진들에 라우팅
        → SignalEngine 이 4h OB 감지 / 1h 진입·청산 판정
          → 엔진이 이벤트 emit → registry가 "구독 설정 목록(configIds)"을 붙여 재방출

    [entry 이벤트]  (엔진이 active 전환 = 진입 시점)
      → ev.configIds 각각에 대해 tryEntry(st, sig)
        → executeEntry(sig, {creds, investUsdt, leverage})
           즉 "신호 1개 → 구독한 여러 사용자 계정에 각자 주문" (fan-out)
        → 진입 시 거래소 preset TP/SL1 함께 설정됨

    [exit 이벤트]  (sl2 / sl3 / timeout 만)
      → 보유 중이고 heldKey 일치하는 설정만 closeBySignal()
        → executeSL2Exit(creds) 시장가 청산 → settle()
      ※ tp / sl1 은 거래소 preset이 자동 체결 → 아래 포지션 폴링으로 감지

  ┌─────────────────────────────────────────────────────────────────────┐
  │ pollPositionCloses() — 20초마다 (TP/SL1 preset 체결 감지)            │
  └─────────────────────────────────────────────────────────────────────┘
    보유 설정마다 hasOpenPosition(creds) 확인
      → 포지션이 사라졌으면 = preset(TP 또는 SL1) 체결됨
      → 현재가로 TP/SL1 판별 → settle()

  ┌─────────────────────────────────────────────────────────────────────┐
  │ refreshPendingOrders() — snapshot 보강                               │
  └─────────────────────────────────────────────────────────────────────┘
    활성 설정마다 거래소 미체결 주문을 조회해서 pendingOrders에 싣는다.
    Bitget 응답은 배열 또는 { entrustedList: [...] } 형태가 올 수 있어 둘 다 처리한다.

  ┌─────────────────────────────────────────────────────────────────────┐
  │ settle() — 청산 정산                                                 │
  └─────────────────────────────────────────────────────────────────────┘
    실현손익(USDT) = 방향 × (청산가 - 진입가) × 수량
      → POST /{id}/pnl 로 Spring 보고
      → 인메모리 포지션 상태 클리어


────────────────────────────────────────────────────────────────────────────
4. 안전장치 (이게 기능보다 우선)
────────────────────────────────────────────────────────────────────────────

  (A) 손실한도 자동중지  [권위 = DB]
      청산마다 워커가 /pnl 보고 → Spring addRealizedPnl:
        realized_pnl 누적 + (누적 ≤ -(invest_usdt × max_loss_pct/100) 이면
        is_active=false, status='STOPPED_LOSS')
      → 다음 폴링에서 그 설정이 active 목록에서 빠짐
        → 워커가 "사라진 설정" 처리로 포지션 청산 + 구독 해제

  (B) 글로벌 Kill Switch  [전체 비상정지]
      admin이 KillSwitchPanel에서 ON → POST /api/admin/kill-switch
        → system_flags.kill_switch = true
      워커가 매 폴링에 /kill-switch 확인 → ON이면 active=[] 취급
        → 전 설정 포지션 청산 + 구독 해제 (단 DB is_active는 유지)
      → OFF로 되돌리면 자동 재개되는 "비상 일시정지" 의미

  (C) 키 격리
      bitget.ts 계정 API는 creds 인자를 받음. 통합 워커는 항상 설정별 creds를
      명시 전달(전역 CREDS 미사용). by-member 키 조회는 env fallback 없음
      → 키 누락 시 남의 키로 주문되는 사고 차단.

  (D) 재시작 안전 (reconcile)
      워커 상태는 인메모리라 재시작 시 유실 → 설정 추가 때 거래소 실포지션을
      조회해 activeEntry 복구 → 중복 진입 방지.


────────────────────────────────────────────────────────────────────────────
5. Before / After (단일 봇 → 멀티유저)
────────────────────────────────────────────────────────────────────────────

  [BEFORE] 프로세스 1개 = 봇 1개 = 심볼 1개 = 운영자 키 1개
    - bot.ts 가 전역 CREDS, CandleFeed 1개, SignalEngine 1개로 단일 심볼만.
    - 일반 사용자는 키만 저장될 뿐 매매 불가.
    - 심볼/사용자 늘면 프로세스도 선형 증가.

  [AFTER] 프로세스 1개 = 통합 워커 = N설정(N사용자 × N심볼)
    - MarketFeed 1개(심볼 합집합) + EngineRegistry(엔진 공유) + 설정별 주문.
    - 같은 (심볼+전략+params) 설정은 엔진 1개를 공유 → 중복 계산 제거.
    - 주문/청산 단계에서만 설정별 키·투자금으로 분리.

6. 화면 표시 기준 (2026-06-04 추가 반영)
────────────────────────────────────────────────────────────────────────────

거래탭(/mobile/#/orders)
  - 상단 온라인 상태: Bot1~7 합산이 아니라 워커 alive 기준으로 "1/1 Worker" 표시.
  - 계정 현황: Unified Worker ONLINE, 활성 설정 수, 엔진 수, 심볼 수, 설정 목록 표시.
  - 총자산: 워커 snapshot.mainBalance 기준.
    · 1 USDT 미만은 0.3894처럼 4자리까지 표시.
  - 포지션 탭: snapshot.configs 중 hasPosition=true인 설정을 포지션으로 표시.
    · MAIN 계정 수동 포지션은 snapshot.mainPositions로 함께 표시.
  - 미체결 탭: snapshot.pendingOrders를 표시.
    · MAIN 계정 수동 미체결은 snapshot.mainPendingOrders로 함께 표시.
  - 모니터링 탭: snapshot.trackers를 표시.
    · scanning/waiting_entry/active 단계별 카운트와 Worker 필터를 사용.
  - 거래내역: 아직 워커 trade log 영속화가 없어 빈 화면이 정상.

마켓탭(/mobile/#/)
  - 상단 "총 자산"은 레거시 botResults/localStorage가 아니라
    /api/admin/worker/status의 snapshot.mainBalance를 사용.

자산탭(/mobile/#/assets)
  - Overview/Futures 모두 워커 snapshot을 기존 BotState 형태로 변환해서 표시.
  - Total balance / Total assets / Wallet balance / USDT 행은 같은 mainBalance 기준.
  - 포지션이 생기면 snapshot.configs의 포지션 정보로 미실현 손익 계산에 반영.

8. 아직 안 된 것 / 주의 (실가동 전 체크리스트)
────────────────────────────────────────────────────────────────────────────
  □ 실거래 E2E 검증 — 소액으로 2설정 1신호→2주문, 손실한도 모의, kill 테스트
     (현재까지는 컴파일/프론트 빌드/워커부팅/웜업안전성/화면 snapshot 표시 검증)
  □ 상태 DB 영속화(trade_positions/trade_logs) — 현재 워커 상태는 인메모리.
     reconcile로 재시작은 막지만, 청산 이력의 영속 기록은 아직 없음.
     그래서 거래탭 "거래내역"은 워커 trade log 저장 기능 전까지 비어 있을 수 있음.
  □ 실시간 mid 터치 진입 — 현재는 엔진 'entry' 이벤트(1h 종가 기준)라
     레거시 bot.ts의 실시간 워처보다 진입이 약간 늦을 수 있음.
  □ 출금권한 자동차단 — Bitget 키 권한 스코프 조회가 불명확해 미완성.
     현재는 "출금권한 없는 키만 등록" 운영 규칙으로 커버.
  □ invest_usdt 합 ≤ 잔고 — 일반 사용자 키 1개 = 한 계정 잔고 공유.
     Spring은 거래소 잔고 조회 불가 → 워커 부팅 가드에서 보강 예정.
