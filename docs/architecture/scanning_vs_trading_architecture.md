# 아키텍처 업데이트: 스캐닝과 자동매매의 완벽한 분리 🚀

## 1. 개요 및 목적
기존 시스템은 "전체 시작" 버튼을 누르는 순간 웹소켓(모니터링) 연결과 함께 타점 발생 시 즉시 실전 주문(매매)이 나가는 일체형 구조였습니다. 
사용자의 니즈("모니터링만 켜두고 구경하다가 원할 때 매매를 켜고 싶다")를 반영하여, 시스템 아키텍처를 **"스캐닝(분석)"**과 **"자동매매(실행)"** 두 가지 독립적인 단계로 분리했습니다.

## 2. 핵심 구현 아이디어: 백엔드/DB 변경 최소화
- 본래 상태값을 세분화하려면 DB의 스키마 변경(`is_active` 외에 `is_trading` 컬럼 추가)과 Java 백엔드의 DTO/엔티티/컨트롤러 수정 등 대대적인 공사가 필요합니다.
- 이를 우회하고 초고속으로 안정적인 배포를 하기 위해, DB 구조 변경 없이 기존에 존재하던 **JSON 설정값 컬럼(`params`)에 `tradeEnabled`라는 속성을 추가**하는 스마트한 아키텍처를 적용했습니다.

## 3. 프론트엔드 UI: 직관적인 2단계 제어 구조
`자동매매` 설정 페이지의 봇 그룹 제어 영역에서 두 가지 제어 버튼이 분리되었습니다:
- **[▶ 스캐닝 시작 / ■ 스캐닝 종료]**:
  - 기존의 `active` 상태를 제어합니다.
  - 봇이 차트 데이터를 받고 타점(하모닉 패턴 등)을 스캐닝하는 백그라운드 엔진을 가동시킵니다.
  - 이 단계에서는 실제 자금이 들어가는 매매가 이루어지지 않습니다.
- **[🔥 자동매매 켜기 / ⏸ 자동매매 끄기]**:
  - `params.tradeEnabled` 상태를 제어합니다.
  - 스캐닝 중에 타점이 포착되었을 때 비트겟에 실제 주문을 넣을지 말지를 결정합니다.
  - 안전을 위해 스캐닝이 꺼져 있을 때는 자동매매 버튼이 비활성화되도록 방어 로직이 짜여 있습니다.

## 4. 백엔드(Node.js Worker) 방어 로직 추가
프론트엔드에서 변경한 `tradeEnabled` 상태를 백엔드 봇 엔진이 즉시 인지하여 주문을 차단합니다.
```typescript
// unified-worker.ts (주문 진입 함수 내)
async function tryEntry(st: ConfigState, sig: EntrySignal, key: string): Promise<void> {
  if (!tradingEnabled) return;  // 글로벌 자동매매 OFF
  
  // 새로 추가된 종목별 매매 옵션 방어 로직
  if (st.cfg.params?.tradeEnabled === false) {
    console.log(`[Worker] ⚠️ 매매 옵션 OFF — 진입 스킵 | cfg=${st.cfg.id} ${sig.symbol}`);
    return;
  }
  // ...실제 주문 실행 로직
}
```

## 5. 결론 및 기대효과
- **안전성 극대화**: 사용자는 실전 투입 전 충분히 봇의 성능(차트 분석 및 패턴 발견율)을 모니터링 탭에서 관전할 수 있습니다.
- **가시성 향상**: 스캐닝만 켜진 코인들도 모니터링 화면에 화려하게 표시되므로, 봇이 어떤 패턴을 포착하고 있는지 실시간으로 체감할 수 있습니다.
- **서버 무중단 적용**: 복잡한 스키마 변경이 없었기 때문에 시스템을 멈추지 않고 즉시 핫 픽스(Hot Fix) 수준으로 새로운 아키텍처를 도입할 수 있었습니다.
